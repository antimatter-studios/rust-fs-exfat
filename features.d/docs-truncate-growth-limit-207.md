## Writing

| Truncate growth on Linux kernels without ValidDataLength support | Known platform limitation, no writer change: growing a file with `truncate` keeps ValidDataLength at the written prefix and writes no zeros past it, as exFAT sections 7.6.5 and 7.6.6 allow (owner decision on #207). On Linux kernels without ValidDataLength support (observed on 6.1.0-42-cloud-arm64) such a file reads as its written prefix: its size is ValidDataLength and its bytes are that prefix. This crate's strict reader, relan/exfat, the read-only macOS driver, exfatprogs `fsck.exfat -n` and relan `exfatfsck -n` read or accept the full DataLength with zero fill. The kernel matrix asserts the valid-prefix view exactly at 512 and 4096 bytes per sector; it is to be replaced by full-DataLength equality if the guest kernel starts returning DataLength; #187 adds the relan cross-check `tests/third.rs::the_kernels_truncate_growth_view_is_exactly_the_valid_prefix` | Unreleased (#207) | #207 | `tests/kernel.rs::the_kernel_reads_every_kind_of_write_by_this_crate` (scoped valid-prefix comparison), `tests/oracle/write.rs` (macOS truncate growth) |
